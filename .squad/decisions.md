# Squad Decisions

## Active Decisions

### 2026-09-11: Architecture — physiological measurement recording

**By:** Lead (requested by Cyrille NDOUMBE)

**Context:**
The physiotrack project needs to expose an API for recording physiological measurements
of several types (heart rate, sleep, activity, ...), each attached to a `subject_id`
provided by the caller and identified internally by a system-generated `id`.
Existing stack: FastAPI, uv, pytest, httpx. Existing endpoint: `GET /health`.

**Decision:**

1. **Common schema (Pydantic, classic inheritance):**
   - `MeasurementBase`: `id: UUID` (generated, `default_factory=uuid4`), `subject_id: str`
     (provided by the caller, non-empty), `dateOfMeasure: datetime`.
   - Each specific type inherits from `MeasurementBase` and adds a discriminant `type`
     field `type: Literal[MeasurementType.X]` plus its own fields:
     - `HeartRateMeasurement(bpm: int)`
     - `SleepMeasurement(duration_minutes: int, quality_score: float | None)`
     - `ActivityMeasurement(steps: int, calories: float | None)`
   - `Measurement = Annotated[Union[HeartRate, Sleep, Activity], Field(discriminator="type")]`
     → native Pydantic validation + OpenAPI `oneOf` automatically generated by FastAPI.
   - Adding a new type = adding a class + the entry in the union. No schema migration
     needed for existing types.
   - Skeleton created: [src/schemas/measurement.py](../../../src/schemas/measurement.py).

2. **Subject identifier (`subject_id`):**
   - Provided by the caller, carried in the URL (path param), not in the body:
     `POST /subjects/{subject_id}/measurements`.
   - Reason: this is a resource "owned" by the subject — classic REST wants this in the
     path; it also avoids an inconsistency if the body contained a `subject_id` different
     from the call context.
   - Validation: non-empty `str` for now (no format imposed). If a structured format is
     ever required (e.g., patient identifier from a third-party system), it could be
     constrained via an `Annotated[str, StringConstraints(...)]` or a dedicated type.
   - No prior existence check for the subject (no `Subject` entity in storage) — the
     subject is implicit, created "on the fly" by its first measurement.

3. **Generating the measurement's system identifier:**
   - `uuid4()`, generated on the service side (not on the client side, not in the schema
     exposed as input).
   - Justification: no external dependency, no need for chronological sort by ID at this
     stage (`dateOfMeasure` already carries that information), broadly supported by all
     future storage options (SQL, NoSQL). ULID was considered (lexicographically sortable
     ID) but rejected for now: additional dependency not justified without a need for
     sorting by ID. To be reconsidered if cursor-based pagination on the measurement ID is
     ever needed.

4. **Shape of the endpoint(s):**
   - **A single generic endpoint** `POST /subjects/{subject_id}/measurements` accepting the
     discriminated `Measurement` schema in the body (the `type` field indicates which
     sub-schema to apply), rather than one endpoint per type
     (`POST /subjects/{subject_id}/heart-rate`, etc.).
   - `GET /subjects/{subject_id}/measurements` to list, with an optional `?type=heart_rate`
     filter.
   - Justification: a single route to maintain, a single validation/storage layer, adding
     a new type = adding a class in the union without a new route. The discriminated union
     still provides correct per-type OpenAPI documentation (`oneOf`), so readability on the
     doc side is not lost.
   - Accepted trade-off: clients must read the `type` discriminant rather than infer the
     type from the URL — deemed acceptable given the gain in server-side simplicity.

5. **Proposed file structure under `src/`:**
   ```
   src/
     main.py
     routers/
       health.py
       measurements.py        # POST/GET endpoints (to be implemented by Backend Dev)
     schemas/
       __init__.py
       measurement.py         # Pydantic schemas (skeleton created by Lead)
     services/
       measurement_service.py # business logic: create(), list(), validation
     storage/
       __init__.py
       repository.py          # MeasurementRepository interface/Protocol
       in_memory.py           # InMemoryMeasurementRepository (default implementation)
   ```
   - The `router` calls the `service`, the `service` calls the `repository` (abstraction).
     This isolates the storage choice from the rest of the code.

6. **Storage strategy:**
   - **In-memory** to start (`dict[str, list[Measurement]]` key = `subject_id`), behind a
     `MeasurementRepository` interface (Protocol) with `add()` / `list_by_subject()`.
   - No DB decision at this stage — stay pragmatic as long as the persistence/volume need
     is not known. If a DB is decided later (Postgres via SQLModel probably, consistent
     with the FastAPI ecosystem), only the `repository` implementation changes, not the
     `router` nor the `service`.

7. **HTTP response codes:**
   - `POST /subjects/{subject_id}/measurements` → `201 Created`, body = the created
     measurement (with generated `id` and echoed `subject_id`/`dateOfMeasure`).
   - `GET /subjects/{subject_id}/measurements` → `200 OK`, body = list of measurements
     (empty list if subject unknown — no `404`, since there is no `Subject` entity to
     "find").
   - Payload validation errors (unknown type, missing field) → `422` (default
     FastAPI/Pydantic behavior, no custom code needed).

**Alternatives considered:**
- Discriminated union vs. plain inheritance without a discriminant: rejected, we would
  lose strict per-type validation and the OpenAPI would be less precise.
- One endpoint per measurement type: rejected for now (over-fragmentation of routes), but
  reversible if a type requires validation/response logic radically different from the
  others.
- `subject_id` in the body rather than the URL: rejected, less RESTful, risk of
  URL/body inconsistency.
- ULID instead of uuid4: rejected for now, no identified need for sorting by ID.
- Immediate DB choice (Postgres, SQLite, etc.): rejected, over-engineering as long as the
  real persistence need is not scoped; the `repository` abstraction makes this choice
  deferrable without a migration cost for the rest of the code.

**Consequences:**
- `pydantic` must be added explicitly to dependencies if we want to pin its version
  (currently pulled transitively by `fastapi`) — to be checked by Backend Dev in
  `pyproject.toml`.
- In-memory storage means data is lost on process restart — acceptable during the
  development phase, to be clearly documented so it is not a surprise in a demo.
- No authentication/authorization planned at this stage on `subject_id` (any caller can
  write for any `subject_id`) — a point to be settled by Security before any deployment
  beyond a dev environment.

**Next steps:**
- **Backend Dev**: implement `routers/measurements.py`, `services/measurement_service.py`,
  wire it to the repository; check `pydantic` in `pyproject.toml`.
- **Data Engineer**: implement `storage/in_memory.py` behind the `repository.py`
  interface; assess if/when a real DB becomes necessary and which one.
- **Security**: decide on authentication/authorization related to `subject_id` (who is
  allowed to write/read a given subject's measurements) before any deployment.
- **Tester**: write pytest tests for `type` discriminant validation, error cases (unknown
  type, missing field), the `?type=` filter on GET, and data isolation between different
  `subject_id` values.

### 2026-09-11: Architecture — vertical slice reorganization

**By:** Lead (requested by Cyrille NDOUMBE)

**Context:**
Two new directives were issued: (1) all documents authored from now on must be in English
(public repository); (2) the project must follow a **vertical slice architecture** — code
grouped by feature/use case, not by technical layer. The previous structure used horizontal
top-level folders (`routers/`, `schemas/`, planned `services/`, `storage/`) that would have
mixed all features' routers together, all features' schemas together, etc.

**Decision:**

1. **New folder structure under `src/`:**
   ```
   src/
     main.py
     features/
       health/
         __init__.py
         router.py          # GET /health (trivial slice — no schema/service needed)
       measurements/
         __init__.py
         schemas.py          # Pydantic discriminated-union schemas (skeleton)
         # router.py, service.py, repository.py to be added by Backend Dev / Data Engineer
   ```
2. **Rule:** each feature folder under `src/features/` is self-contained — router, schemas,
   service, repository for that feature live together. No shared top-level `routers/`,
   `schemas/`, `services/`, `storage/` folders spanning multiple features. Shared/common
   code (if any emerges) goes in a dedicated `src/common/` (or similar) folder, created only
   when a real cross-feature need appears — not preemptively.
3. **Rationale:** vertical slices keep each feature's concerns (endpoint, validation, business
   logic, storage) co-located, so adding, changing, or removing a feature touches one folder
   instead of four scattered ones. This scales better than horizontal layering as the number
   of measurement types / features grows.

**Migration performed:**
- `src/routers/health.py` → `src/features/health/router.py` (content unchanged).
- `src/schemas/measurement.py` → `src/features/measurements/schemas.py` (content unchanged;
  it was already in English, so no translation was needed despite the initial note).
- `src/main.py` updated: import changed from `routers.health` to `features.health.router`.
- Old `src/routers/` and `src/schemas/` folders removed entirely (nothing else referenced them).
- `test/test_health.py` required no changes — it imports `main` from `src` via `sys.path`
  manipulation, not the removed folders.
- `uv run pytest` run after migration: 1 passed.

**Consequences / guidance going forward:**
- **Backend Dev**: when implementing the measurements endpoints, add `router.py`,
  `service.py`, and `repository.py` inside `src/features/measurements/` alongside the
  existing `schemas.py` — do not create a top-level `routers/` or `services/` folder.
- **Data Engineer**: the in-memory repository implementation for measurements also belongs
  inside `src/features/measurements/` (e.g. `repository.py` or a small `storage/` sub-folder
  local to that feature only if multiple storage implementations are needed).
- **Any new feature** (a new measurement type is NOT a new feature — it's a new class in the
  existing `measurements` slice's schema union; a genuinely new capability, e.g. "subjects
  management" or "reports", is a new feature) → create a new folder under `src/features/`
  with only what that feature needs.
- From now on, all decisions, docs, and code comments/docstrings authored by this team are
  written in English. The prior decision entry (2026-09-11, "Architecture — enregistrement de
  mesures physiologiques") remains in French — historical, append-only, not retroactively
  translated.

**Alternatives considered:**
- Keeping the horizontal layering proposed in the previous decision: rejected per new
  explicit directive — horizontal layers don't scale well once several measurement-type
  features (or entirely new features) are added.

**Next steps:**
- Backend Dev / Data Engineer: continue measurements feature work inside
  `src/features/measurements/` per the structure above.
- Tester: test files can remain flat under `test/` for now (mirroring feature names, e.g. a
  future `test/test_measurements.py`), no vertical-slice requirement imposed on tests.
